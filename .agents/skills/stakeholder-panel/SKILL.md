# stakeholder-panel

## 호출 조건 및 제외 조건

제품/사용자 경험에 영향을 주는 변경·시안·기획·우선순위·수익화·출시 판단에 호출한다. 아키텍처·코드 리뷰·운영·하네스 갱신 및 QA·Android 네이티브·아트·보안·사용자 리서치·제품 분석에도 관련 역할을 호출한다. 단순 CI/오타는 technical route로 보호 스킬만 적용한다.

## 참조 문서

`docs/STAKEHOLDER_HARNESS.md`, `docs/PRODUCT_PHILOSOPHY.md`, `docs/DESIGN_SYSTEM.md`, `docs/DEVELOPMENT_RULES.md`.

## 실행 절차

실제 기준 자료를 읽고 route·modifier를 선택한다. 신규 역할 선택 기준은 하네스 3.2 문서에 따른다. Android 릴리스에는 release + android, 실제 데이터/인증/동기화 변경에는 data(보안 검토만의 security로 대체 금지), 아트는 art, 사용자 조사·지표는 research/analytics를 빠뜨리지 않는다. `node scripts/select-stakeholders.mjs <route> [modifier ...]`의 결과에 맞춰 역할/보호 스킬을 읽는다. 공통 브리프를 만든 뒤 각 역할의 기준·가중치를 사용해 독립 관점 검토 → 구체적 반박(반례·실패 조건·근거) → 제안자의 재반박(수용/기각/보류 사유) → 수정 → 동일 기준 재평가를 한 라운드로 실행한다. selector의 minRounds~rounds 범위에서 반복하며 최대 3회. 최소 횟수 이후 실질 신규 이슈와 핵심 이견이 없고 게이트를 만족해야 종료한다. 3회 후 미해결 P0/P1 또는 핵심 위험은 보류한다. 각 쟁점의 ID·담당·근거·결정·수용 조건과 시안 수정본을 기록한다. 실제 독립 에이전트를 실행하지 않았으면 구조화된 관점 검토임을 명시한다. QA 독립 인수 의견은 실제 재현 증거와 구분하고 보안 위험·필수 출시 게이트는 협의로 통과시키지 않는다. 리서치/분석은 실제 연구·측정/가설 및 미확인(N/E)을 분리한다. 설계/구현과 검증을 구분하고 P0/P1·데이터/접근성/출시 게이트를 평균으로 상쇄하지 않는다. 사용자 확정 정책과 승인 범위가 최상위다.

## 금지 사항

모든 작업에 무조건 전 역할 호출, 전문가/실제 사용자 조사 사칭, 근거 없는 숫자·점수, 의견 불일치 은폐, 보호 스킬 우회, 승인 없는 운영 변경 금지.

## 완료 기준

관련 역할·검토 근거·채택/기각·수정·재검토 및 실행 검증/미확인 항목이 명시되고 핵심 위험이 남으면 보류한다.

## 실패 시 대응

근거를 보강하고 역할 이견을 재검토한다. 실기기/사용자 조사 부족은 추측을 사실화하지 말고 미확인으로 기록한다. P0/P1 미해결 시 실행/출시 범위를 축소하거나 보류한다.
